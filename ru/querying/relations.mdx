Модели Volan связаны друг с другом через поля, помеченные `@relation`. Когда вы выполняете запрос на чтение, связанные модели **не загружаются автоматически** — их нужно явно запросить в блоке `include { }`. Такой подход делает стоимость запросов явной и предсказуемой, а также позволяет Volan загружать каждую связь одним пакетным запросом вместо одного запроса на каждую строку.

## Включение связей через `include { }`

Добавьте блок `include { }` в любой вызов `findMany`, `findFirst`, `findFirstOrThrow`, `findUnique` или `findUniqueOrThrow`. Внутри блока назовите связи, которые хотите загрузить.

<CodeGroup>

```kotlin Kotlin
val users = db.user.findMany {
    include {
        posts {}
        profile {}
    }
}

users[0].posts    // List<Post>
users[0].profile  // Profile? (null, если у пользователя нет профиля)
```

```java Java
List<User> users = db.user().findMany(q -> q
    .include(i -> i
        .posts()
        .profile()
    )
);
```

</CodeGroup>

<Note>
  Опциональные связи «один-к-одному» возвращают `null`, когда связанной записи нет. Обязательные связи (не nullable в схеме) всегда non-null, если данные целостны.
</Note>

## Фильтрация и пагинация включённых связей

Каждая связь в `include { }` принимает собственные выражения `where`, `orderBy`, `take` и `skip`. Фильтры применяются только к включённой связи, но не к родительскому запросу.

```kotlin
val users = db.user.findMany {
    include {
        posts {
            where { draft eq false }
            orderBy { createdAt.desc() }
            take = 5
        }
        profile {}
    }
}
// У каждого пользователя не более 5 опубликованных постов, свежие впереди
```

Это особенно полезно для «превью»-сценариев — например, показать три самых свежих комментария к каждому посту в ленте.

## Вложенные include

Связи можно вкладывать на любую глубину. Каждый уровень загружается своим пакетным запросом.

```kotlin
val users = db.user.findMany {
    include {
        posts {
            include {
                comments {
                    orderBy { createdAt.asc() }
                }
                tags {}
            }
        }
    }
}

users[0].posts[0].comments  // List<Comment>
users[0].posts[0].tags      // List<Tag>
```

<Tip>
  Глубокое вложение удобно, но добавляет один поход в базу на каждый уровень связи. Профилируйте количество запросов на этапе разработки через логгер запросов Volan, если подозреваете лишнюю глубину.
</Tip>

## Как Volan загружает связи — без N\+1 по архитектуре

Самая частая ошибка производительности в ORM — **проблема N\+1**: выбирается список из N родительских записей, а затем отдельный запрос для загрузки потомков каждой из них. Стратегия загрузки Volan делает такое структурно невозможным.

Когда вы включаете связь, Volan:

1. Запускает родительский запрос и собирает все первичные ключи.
2. Выполняет **один** запрос `WHERE fk IN (?, ?, ...)` на каждую связь этого уровня, независимо от количества родительских строк.
3. Сшивает результаты с родительскими объектами в памяти.

```text
// Для 1000 пользователей с включёнными постами Volan выполняет ровно два запроса:
SELECT * FROM users WHERE ...;
SELECT * FROM posts WHERE user_id IN (1, 2, 3, ..., 1000);
```

Если список в `IN` превысит лимит параметров драйвера, Volan автоматически разбивает его на пакеты и объединяет результаты — вам не нужно этим заниматься.

## Обращение к загруженным и незагруженным связям

Если вы обращаетесь к связи на экземпляре модели, которая **не была** включена в запрос, Volan бросает `VolanRelationNotLoadedException`, а не выполняет ленивый запрос.

```kotlin
val users = db.user.findMany {}  // без блока include

users[0].posts  // ❌ бросает VolanRelationNotLoadedException
```

Такое строгое поведение предотвращает случайную ленивую загрузку и делает количество запросов явным.

### Проверка, загружена ли связь

У каждой связи есть сгенерированное свойство-флаг `is<Relation>Loaded`, которое можно проверить перед обращением:

```kotlin
if (user.isPostsLoaded) {
    render(user.posts)
} else {
    renderPlaceholder()
}
```

### `<relation>IfLoaded`

Кроме того, у каждой связи есть сгенерированное свойство `<relation>IfLoaded`, возвращающее загруженное значение или `null` без исключения:

```kotlin
val posts = user.postsIfLoaded  // List<Post>? — null, если не загружено
```

Это удобно в общем коде маппинга моделей в DTO, где один и тот же тип может иметь загруженные связи или не иметь их в зависимости от места вызова.

## Фильтры по связям в `where { }`

Связи можно использовать как критерий фильтрации, не включая их в результат. Полная документация — в разделе [Фильтрация](/ru/querying/filtering), но вот краткая справка:

### `some { }` — хотя бы одна связанная запись подходит

```kotlin
db.post.findMany {
    where {
        tags { some { name eq "kotlin" } }
    }
}
```

### `none { }` — ни одна связанная запись не подходит

```kotlin
db.user.findMany {
    where {
        posts { none { draft eq true } }
    }
}
```

### `every { }` — все связанные записи подходят

```kotlin
db.user.findMany {
    where {
        posts { every { draft eq false } }
    }
}
```

### `matches { }` и `notMatches { }` — для связей «к одному»

```kotlin
db.post.findMany {
    where {
        author { matches { role eq Role.ADMIN } }
    }
}
```

<Note>
  Volan использует `matches` / `notMatches` вместо `is` / `isNot`, потому что `is` — зарезервированное слово в Kotlin.
</Note>

Эти фильтры по связям не загружают связанные записи в память — возвращаются только родительские строки.

## Эквивалент на Java

```java
List<User> users = db.user().findMany(q -> q
    .include(i -> i
        .posts(p -> p
            .where(w -> w.draft().eq(false))
            .orderBy(Post_.CREATED_AT.desc())
            .take(5)
        )
        .profile()
    )
);
```
