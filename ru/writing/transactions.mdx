Транзакции позволяют объединить несколько операций базы в единую атомарную единицу — либо все успешны, либо ни одна. Блок `db.transaction {}` в Volan выражает это напрямую в Kotlin или Java со встроенной поддержкой уровней изоляции, автоматическими повторами и вложенными транзакциями через savepoint.

## Базовая транзакция

Оберните любую последовательность операций Volan в `db.transaction {}`, чтобы выполнить их атомарно. Блок получает клиент, ограниченный транзакцией (`tx`), через который должны выполняться все операции, и возвращает значение своего последнего выражения.

```kotlin
val post = db.transaction { tx ->
    val user = tx.user.create {
        email = "new@example.com"
    }

    tx.post.create {
        title  = "First Post"
        author.connect { id eq user.id }
    }
}
// `post` — сущность Post, созданная внутри транзакции
```

Если любая операция в блоке бросает исключение, Volan откатывает всю транзакцию и пробрасывает исключение дальше. Вызывать `rollback()` вручную никогда не нужно.

## Уровни изоляции

Можно передать значение `Isolation` первым аргументом в `db.transaction`, чтобы управлять тем, как транзакция взаимодействует с конкурентными записями из других соединений.

```kotlin
val result = db.transaction(Isolation.SERIALIZABLE) { tx ->
    // все чтения и записи здесь полностью сериализуемы
}
```

### Доступные уровни

<ParamField path="Isolation" type="enum">
  Управляет видимостью незафиксированных изменений из других транзакций.

  - **`READ_UNCOMMITTED`** — Может читать строки, изменённые другими незавершёнными транзакциями (грязные чтения разрешены). Наивысшая пропускная способность, наименьшая согласованность.
  - **`READ_COMMITTED`** — Видит только строки, зафиксированные до начала каждого выражения. По умолчанию в большинстве баз.
  - **`REPEATABLE_READ`** — Повторное чтение той же строки в одной транзакции всегда возвращает те же данные, даже если другая транзакция зафиксировала изменения между чтениями.
  - **`SERIALIZABLE`** — Полная изоляция; транзакции ведут себя так, как будто выполнялись последовательно. Самый безопасный, но подвержен конфликтам.
  - **`DEFAULT`** — Использует тот уровень изоляции, который настроен на соединении с базой. Рекомендуется, если нет конкретной цели.
</ParamField>

<Tip>
  Предпочитайте `Isolation.DEFAULT` для общего кода приложения и переходите к `SERIALIZABLE` только тогда, когда нужно предотвратить фантомные чтения или аномалии write-skew, например, в финансовых сценариях или складских рабочих процессах.
</Tip>

### Ошибки сериализации

При использовании `Isolation.SERIALIZABLE` (или `REPEATABLE_READ` в некоторых базах) база может прервать транзакцию из-за конфликта с конкурентной транзакцией. В этом случае Volan бросает `VolanTransactionException` с `retryable = true`. Сочетайте этот уровень изоляции с `RetryPolicy`, чтобы Volan выполнял повторы автоматически.

```kotlin
val result = db.transaction(Isolation.SERIALIZABLE, RetryPolicy.DEFAULT) { tx ->
    // автоматически повторяется до 3 раз при ошибке сериализации
}
```

## Политики повторов

`RetryPolicy` управляет тем, сколько раз Volan повторяет транзакцию после повторяемой ошибки и сколько ждёт между попытками.

<ParamField path="RetryPolicy" type="object">
  Настраивает автоматическое поведение повторов для транзакций.

  - **`RetryPolicy.NONE`** — Нет повторов. Транзакция выполняется один раз; при ошибке исключение сразу пробрасывается.
  - **`RetryPolicy.DEFAULT`** — 3 попытки, начальная задержка 20 мс, экспоненциальный backoff ×2 (т. е. задержки 20 мс, 40 мс).
  - **Кастомная** — Создайте `RetryPolicy` с нужными вам параметрами.
</ParamField>

```kotlin
// Без повторов
db.transaction(Isolation.READ_COMMITTED, RetryPolicy.NONE) { tx -> /* ... */ }

// Встроенный дефолт: 3 попытки, задержка 20 мс, backoff ×2
db.transaction(Isolation.SERIALIZABLE, RetryPolicy.DEFAULT) { tx -> /* ... */ }

// Кастомная: 5 попыток, начальная задержка 50 мс, множитель ×1.5
val myPolicy = RetryPolicy(attempts = 5, initialDelay = 50, multiplier = 1.5)
db.transaction(Isolation.SERIALIZABLE, myPolicy) { tx -> /* ... */ }
```

<Note>
  Volan повторяет только исключения с `retryable == true` (например, ошибки сериализации). Прикладные исключения — например, `VolanNotFoundException`, брошенное внутри блока, — никогда не повторяются.
</Note>

## Вложенные транзакции

Вызов `tx.transaction {}` внутри уже открытой транзакции возможен. Volan определяет внешнюю транзакцию и использует **savepoint** вместо открытия нового соединения с базой. Это означает, что внутренний блок можно откатить независимо, не затрагивая внешнюю транзакцию.

```kotlin
db.transaction { outer ->
    doSomething(outer)

    outer.transaction { inner ->
        // Здесь используется savepoint, а не новое соединение.
        // Откат здесь отменяет только операции с момента savepoint.
        doSomethingElse(inner)
    }

    doMoreWork(outer)
}
```

<Tip>
  Savepoints — мощный инструмент для частичных откатов. Если `doSomethingElse()` завершился ошибкой, а внутренняя транзакция поймала исключение, внешняя транзакция может продолжаться — отменяются только изменения внутреннего блока.
</Tip>

## Практический пример: перевод кредитов

Следующий пример показывает многошаговый рабочий процесс, который должен успешно выполниться целиком или полностью откатиться. Использование `Isolation.SERIALIZABLE` защищает от двойного списания тех же кредитов конкурентными переводами.

```kotlin
val transfer = db.transaction(Isolation.SERIALIZABLE, RetryPolicy.DEFAULT) { tx ->
    // Списание с отправителя
    val sender = tx.account.update {
        where { id eq senderId }
        data  { credits = sender.credits - amount }
    }

    // Начисление получателю
    val recipient = tx.account.update {
        where { id eq recipientId }
        data  { credits = recipient.credits + amount }
    }

    // Запись перевода
    tx.transfer.create {
        amount      = amount
        fromAccount.connect { id eq senderId    }
        toAccount.connect   { id eq recipientId }
    }
}
```

Если любая из трёх операций бросит исключение — например, если `senderId` не найден, — вся транзакция откатывается и ни один счёт не изменяется. Если происходит конфликт сериализации, `RetryPolicy.DEFAULT` повторяет до трёх раз, перед тем как пробросить исключение.
