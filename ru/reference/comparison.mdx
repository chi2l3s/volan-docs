Выбор библиотеки персистентности — одно из самых значимых решений в JVM-проекте. Каждый инструмент отражает свою философию — где должна быть истина, сколько магии в рантайме допустимо и какие компромиссы стоят того. Эта страница сопоставляет Volan с тремя частыми альтернативами по тому, что важно на практике.

## Кратко

|  | Volan | Hibernate / JPA | Exposed | JOOQ |
| --- | --- | --- | --- | --- |
| **Источник истины** | Файл схемы | Классы с аннотациями | Kotlin-объекты таблиц | База |
| **Типобезопасные запросы** | Сгенерированный DSL | JPQL-строки / Criteria | DSL | Сгенерированный DSL |
| **Рантайм-рефлексия** | Нет на пути маппинга | Обширна | Некоторая | Нет |
| **Декларативные миграции** | Встроены (M6\+) | Внешние (Flyway/Liquibase) | Внешние | Внешние |
| **Вложенные записи** | Встроены | Каскады | Вручную | Вручную |
| **Java-first API** | Да, протестировано в Java | Да | Неловко | Да |
| **Сюрпризы ленивой загрузки** | Нет по дизайну | Часты | Явные | Не применимо |
| **N\+1 по умолчанию** | Невозможен | Част | Явно | Не применимо |

## Schema-first vs class-first vs DB-first

Главная ось дизайна — где определяется схема.

<Tabs>
  <Tab title="Volan — файл схемы">
    Вы пишете один файл `.volan`. Volan генерирует и миграцию базы, и типобезопасный код клиента из него. Строго одно место для изменений, которое версионируется как любой код.

    ```volan
    model Post {
      id        Int      @id @default(autoincrement())
      title     String
      published Boolean  @default(false)
      author    User     @relation(fields: [authorId], references: [id])
      authorId  Int
    }
    ```

    Запуск `volan generate` после изменения схемы перегенерирует клиента и при необходимости производит миграцию.
  </Tab>
  <Tab title="Hibernate/JPA — аннотированный класс">
    Модель данных живёт в Java/Kotlin классах. Аннотации несут метаданные маппинга. Генерация схемы возможна, но обычно заменяется внешними инструментами миграции (Flyway, Liquibase) как только проект выходит в продакшен.

    ```java
    @Entity
    @Table(name = "posts")
    public class Post {
        @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
        private Long id;
    
        @Column(nullable = false)
        private String title;
    
        private boolean published = false;
    
        @ManyToOne(fetch = FetchType.LAZY)
        @JoinColumn(name = "author_id")
        private User author;
    }
    ```

    Класс _есть_ схема — но класс, миграция и база в синхроне — ваша ответственность.
  </Tab>
  <Tab title="JOOQ — database first">
    JOOQ читает существующую базу и генерирует типобезопасные DSL-классы. База — источник истины; код нужно регенерировать при каждом изменении.

    Подходит командам, где DBA владеет схемой, но инвертирует рабочий цикл для greenfield-проектов.
  </Tab>
  <Tab title="Exposed — Kotlin-объекты таблиц">
    Exposed описывает таблицы Kotlin-объектами и предоставляет и DSL, и DAO. Файла схемы нет; определения таблиц живут рядом с кодом приложения. Миграции — вручную или через сторонние инструменты.
  </Tab>
</Tabs>

## Никакой ленивой загрузки — никогда

Это возможно, самое резкое рантайм-различие между Volan и Hibernate.

В Hibernate ассоциация `@ManyToOne` или `@OneToMany` с `FetchType.LAZY` не загружается, пока вы не обратитесь к полю. Если сессия ещё открыта — Hibernate отправит ещё один SELECT. Если закрыта — вы получаете `LazyInitializationException`. В Spring-приложениях это часто приводит к антипаттерну «open session in view».

**Позиция Volan другая:** связи никогда не загружаются, если вы их явно не запросили.

```kotlin
// Связи нужно явно включать в месте вызова
val post = db.post.findUnique {
    where { id eq postId }
    include {
        author()          // загружаем автора
        comments {        // загружаем комментарии…
            include { author() }
        }
    }
}

// Обращение к post.author без include бросит
// VolanRelationNotLoadedException сразу — никаких тихих запросов, никакой зависимости от сессии.
```

Это значит:

- Каждый SELECT виден в коде.
- Связанные данные можно загружать на любом слое приложения, не только пока транзакция открыта.
- `VolanRelationNotLoadedException` точно говорит, какую связь добавить.

## N\+1 структурно невозможен

N\+1 возникает, когда код итерирует по записям и обращается к связям, вызывая отдельный запрос на каждую строку. Hibernate, Exposed и голый JDBC подвержены этой проблеме.

Volan исключает N\+1 по конструкции: нельзя итерировать по результатам и триггерить новые запросы, потому что нет неявного механизма запроса. Все данные для загрузки должны быть объявлены в блоке `include {}` до выполнения.

```kotlin
// Один запрос, а не 1 + N
val users = db.user.findMany {
    include { posts() }
}
users.forEach { user ->
    // user.posts уже в памяти — больше запросов не будет
    println("${user.name} has ${user.posts.size} posts")
}
```

## Вложенные записи

Создание родительской записи и связанных детей в одной атомарной операции в большинстве ORM требует аккуратной координации.

<Tabs>
  <Tab title="Volan">
    Вызовы `create` и `update` принимают дерево вложенных записей, зеркалящее граф связей схемы. Всё в одном вызове выполняется в одной транзакции автоматически.

    ```kotlin
    val newUser = db.user.create {
        data {
            name  = "Alice"
            email = "alice@example.com"
            posts = createMany {
                data(
                    PostCreateInput { title = "Hello, world!" },
                    PostCreateInput { title = "Second post" }
                )
            }
        }
    }
    ```
  </Tab>
  <Tab title="Hibernate/JPA">
    Hibernate поддерживает каскады через `CascadeType`. Дочерние сущности сохраняются автоматически при persist родителя, если каскад настроен, а ассоциация управляется верно (что источник тонких багов).

    ```java
    user.setPosts(List.of(post1, post2));
    post1.setAuthor(user);
    post2.setAuthor(user);
    entityManager.persist(user); // каскадит на posts
    ```
  </Tab>
  <Tab title="Exposed / JOOQ">
    Оба требуют выполнять вставки в правильном порядке вручную, получая сгенерированные ID.

    ```kotlin
    val userId = Users.insertAndGetId { it[name] = "Alice" }
    Posts.insert { it[title] = "Hello"; it[authorId] = userId }
    ```
  </Tab>
</Tabs>

## Миграции

| Инструмент | Статус миграций |
| --- | --- |
| **Volan** | `volan migrate dev` генерирует SQL-миграцию из разницы между схемой и базой. `volan migrate deploy` применяет ожидающие миграции в CI/продакшене. Встроено с M6. |
| **Hibernate** | `hbm2ddl.auto=update` не безопасен в продакшене. Большинство команд берет Flyway или Liquibase и пишет миграции вручную. |
| **Exposed** | `SchemaUtils.createMissingTablesAndColumns()` добавляет колонки, но не удаляет и не переименовывает. Миграции продакшена — отдельный инструмент. |
| **JOOQ** | Сначала меняется база, потом регенерируются классы JOOQ. Инструменты миграции внешние. |

## Качество Java API

DSL запросов Volan спроектирован и протестирован в Java как гражданин первого класса. Все билдеры и лямбды API компилируются чисто без unchecked-кастов и raw-типов, а сгенерированные модели — обычные Java-совместимые POJO.

Exposed, напротив, построен в основном для Kotlin. Использовать его из Java возможно, но неловко — много Kotlin extension-функций, object-singletons и ресиверов.

JOOQ и Hibernate имеют крепкие Java API и одинаково комфортны в любом языке JVM.

---

## Рантайм-рефлексия

Hibernate использует рефлексию и runtime-байткод-манипуляции (cglib/ByteBuddy) для ленивых прокси, dirty-checking и инструментированных сущностей. Это замедляет старт, усложняет стектрейсы и мешает GraalVM native image.

Volan не выполняет рефлексии на пути маппинга вообще. Сгенерированные модели — обычные data-классы; движок запросов сопоставляет колонки `ResultSet` с полями через сгенерированный код, а не рефлективные сеттеры. Это даёт:

- Более быстрый старт
- Меньшие native-образы без специальных конфигов
- Стектрейсы, указывающие на ваш код, а не на внутренности прокси

## Когда выбирать Volan

<CardGroup cols={2}>
  <Card title="Greenfield JVM-проекты" icon="seedling">
    Schema-first рабочий цикл Volan самый продуктивный, когда вы проектируете модель с нуля и хотите, чтобы схема базы, миграции и клиент были в идеальной синхронизации без ручной координации.
  </Card>

  <Card title="Команды, обжёгшиеся магией Hibernate" icon="fire-flame-curved">
    Если вы встречали `LazyInitializationException`, таинственные N\+1-регрессии или ошибки каскадов, явность Volan будет предсказуемой альтернативой.
  </Card>

  <Card title="Kotlin или Java на JVM 17+" icon="mug-hot">
    DSL Volan одинаково естественен в Kotlin (с поддержкой корутин) и Java. API проектировался для обоих языков с первого дня.
  </Card>

  <Card title="Проекты для GraalVM native" icon="bolt">
    Нулевая рефлексия на пути маппинга — Volan работает в native image без reflection-конфигов и build-time агентов.
  </Card>
</CardGroup>

<Note>
  Volan пока не лучший выбор для проектов, которым нужно в рантайме работать с схемой-независимыми legacy-таблицами или которые полагаются на переносимость JPA между вендорами через единый диалект JPQL. См. [ROADMAP](https://github.com/thirtyeighttwentysix/volan/blob/main/ROADMAP.md).
</Note>
